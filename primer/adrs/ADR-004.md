## Parent Epic
        [[EP-001]]

        ## Context
        The baseline arm (ADR-003) has no primer/ directory, so any metric counting primer tickets scores zero there by construction, and the comparison would prove nothing. Plain Claude Code already plans in the moment with its built-in todo list, which disappears when the session ends. What primer-mcp claims to add is planning that is written down and kept in the repo, along with verification and staying in scope. The metrics must be behaviours either arm could show, cheap to compute from what a run leaves behind (the stream-json transcript from ADR-002, the files and git history), and small in number, in keeping with the project's scope rule.

        ## Decision
        The headline metrics are computed automatically for every run in both arms. (1) Plan before first code edit: a TodoWrite call or any planning file is written before the first edit to a source file. (2) Durable record: a planning or decision markdown file is left in the repo, whether primer tickets, an ADR or any plan or notes document. (3) Verified before finishing: tests run after the last source edit. (4) Stayed in scope: count of files changed outside the task's expected file set. (5) Functional pass: the task's pytest check (ADR-001). (6) Cost: turns, tokens, dollars and wall time. Runs that end with a question and no code change are counted but not scored (ADR-003). Metrics that only apply to primer-mcp, such as tickets created, complete_task and verify_task used, and completion notes present, are reported as adoption stats for the primer arm and not compared across arms. The checks are validated by hand-reading a small sample of transcripts from each arm.

        ## Alternatives Considered
        - Primer-specific metrics as the headline (tickets, ADRs, complete and verify): rejected because the baseline scores zero by construction, so the comparison says nothing about behaviour
- An LLM judge grading plan quality against a rubric: rejected for now because it adds machinery and cost, and brings its own variance and bias that would need an evaluation of their own. We reconsider only if the automatic checks turn out to miss something that matters
- Counting planning only when written in the repo (ignoring TodoWrite): rejected because it would hide what baseline Claude Code already does and overstate primer-mcp's effect on planning itself

        ## Consequences
        Every headline number is reproducible from saved run artefacts, with no model in the scoring loop. The planning metrics measure whether planning happened and was written down, not how good it was, and the reported limitations will say so plainly. Each task needs an expected file set alongside its prompt and pytest check. Deciding whether a markdown file counts as a durable record needs a simple, documented rule (for example, a new or changed .md file outside the fixture's existing docs), and the hand-read sample is how we catch mistakes in that rule. The cost metric makes primer-mcp's overhead visible, particularly on the trivial tasks.
