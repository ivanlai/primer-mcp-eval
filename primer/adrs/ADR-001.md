## Parent Epic
        [[EP-001]]

        ## Context
        Both arms need the same starting codebase and the same prompts, and the codebase has to reset cleanly between runs. The tasks must draw out the behaviours primer-mcp claims to change: planning, tickets, recorded decisions, completion and verification evidence, scope. They should also test the opposite case, where planning is unnecessary. The eval measures behaviour, not code quality, but a run that plans well and never does the work must not score well.

        ## Decision
        Build a small Python CLI app (about 500-800 lines, with a pytest suite) for this eval, keep it in this repo, and give every run a fresh copy of it. Use 12 tasks: 4 multi-step features, 3 fixes for planted bugs, 2 refactors, 2 trivial changes and 1 ambiguous request. Prompts are plain requests, identical in both arms, and never mention primer-mcp, tickets or planning. Each task has one functional pytest check so that we can see the work was done. Behaviour metrics are left to their own ADR.

        ## Alternatives Considered
        - A pinned open-source project: rejected because the agent may already know it from training, it costs more per run, and tasks on it are harder to check automatically
- SWE-bench-style issues: rejected because they measure code correctness, not planning behaviour, and bring far more machinery than this eval needs
- primer-mcp itself as the target: rejected as circular, since its existing primer/ tickets would show the agent the workflow in both arms
- Only feature, bug and refactor tasks: rejected because it loses the over-planning signal; primer's guidance lets trivial work skip tickets, and the trivial tasks test that

        ## Consequences
        We control the codebase fully and can plant bugs and design tasks for particular behaviours, and runs are cheap to repeat. The cost is realism: a fixture is less messy than a real codebase, so the results show behaviour on small, clean projects. A pinned real repo can be added later if the fixture results are unclear. Twelve tasks is too few to split results by task kind with any confidence, so the headline is a comparison across all tasks.
