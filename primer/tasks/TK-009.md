## Parent Story
[[ST-004]]

## What to do
Build one script that scores every saved run of a batch against the ADR-004 metrics, using only its transcript, final repo and meta.json. It writes one row per run and a summary: per-arm rates with confidence intervals bootstrapped over scenarios, per-scenario differences, cost, and primer-only adoption stats. Write down the rules each metric uses, including what counts as a durable record, as short definitions next to the code.

## Testable Outcome
Offline tests with synthetic transcripts and repos cover each metric rule and the aggregation. Scoring the stub runner's output end to end produces runs.csv and summary.md with no model calls.

## Dependencies
- (none)

## Completion Notes
score.py scores saved runs against the ADR-004 metrics with bootstrapped intervals; 23 offline tests pass; end to end on stub runs

- `scripts/score.py --batch pilot` reads runs/<batch>/ and writes results/<batch>/runs.csv (one row per run) and summary.md: per-arm rates with 95% intervals bootstrapped over scenarios, per-scenario differences (primer − baseline), mean out-of-scope files, cost, turns and duration, and primer-only adoption stats (never compared across arms).
- The metric rules are written in the script's docstring. A durable record is any Markdown file added or changed since the initial commit. Planning-before-edit counts TodoWrite/TaskCreate/TaskUpdate, any primer-mcp tool, or a Markdown write before the first non-Markdown edit.
- Functional runs the scenario's check on a scratch copy of the final repo. `repo_tests` separately records whether the repo's own suite, as the agent left it, passes; this is the "broke something else" signal discussed during ST-002.
- It reuses the validator's pytest helper, so failing and erroring checks are told apart in the same way.

### Details
Known limits, for the pilot's hand-read sample to check: edits made through Bash (sed -i, redirection) aren't seen as code edits, and tests run by any means other than a Bash `pytest` call aren't seen as verification; `asked` is a heuristic (no code edit plus a "?" in the final message); and a new usage README would count as a durable record. The transcript shape (tool_use blocks inside assistant message content; a final result event carrying total_cost_usd, num_turns and duration_ms) matches Claude Code's session logs but hasn't been seen from a real `-p` stream-json run yet. The end-to-end stub run found a runner bug: a relative --claude path broke because sessions run inside the repo copy. It is fixed in run_eval.py (the path is now resolved) with a regression test.
